Available references: R01, R03, R04, E01, R05; SOAP_CONTRACT_MAP.json.
The accepted office/day cache already covers all returned visit IDs. The current
visit-call reader checks patient/caregiver/office/date and explicitly reports
same-subject/day-only evidence. It does not supply authoritative visit linkage
or complete event history. Reuse these boundaries, not a blind cross-record join.

Next bounded build:
- A shared visit details/call-attempt panel, consistent IDs/receipts and a useful
  case queue. Display the current call reader's real scope and limits.
- A separately authorized office-level attempt reader using documented filters
  and cursor fields, with fresh membership proof for returned subjects. Current
  patient-scoped read approval is not silently broadened by this resource pack.
- A scoped GetVisitChangesV4 design and bootstrap/reconciliation strategy so
  changed visits can refresh without repeatedly rescanning every detail.
- Validate source timezone, watermark ties, page completion, deletes, restart and
  cross-office filtering before activating a new feed. No new method is enabled.

Freshness/resource finding:
  functions/src/operations/workspace.ts -> FirestoreWorkspaceRepository.reserveRead
sets a shared 60-read/minute application budget with vendor backoff handling.
The published provider guide has a higher per-method/provider ceiling. These
are different limits. Existing ~36-minute full-scan timing is not proof that HHA
itself permits only 60 reads/minute. Confirm tenant limits and review capacity,
backoff and interactive headroom before any tuning. Existing O03 acceptance stays.

M02 - REASON/ACTION CATALOGS AND CONFIRMATION
Available code:
  hharefs/hha-wdsl.xml
  functions/src/integrations/hhaexchange/contractGates.ts
  functions/src/operations/reads.ts
  functions/src/operations/workspace.ts
  functions/src/operations/recovery.ts
  functions/src/auth/workflowPermissions.ts
Available references: R04-R12, E01, HHA_SUPPORT_QUESTIONS.txt.
Schema includes the three ConfirmVisits variants and VisitCallInOut. Their
supported action semantics are absent from the reviewed guide, so current blocks
remain. GetVisitEditReasonActionTaken has the same missing-guide issue.
GetScheduleBillInfoEditReasons is a documented, implemented reference-read
candidate; its namespace and meaning must be checked against the intended EVV
action. Do not substitute it for an unproved reason/action catalog.

Reusable execution pattern:
Existing workspace proposals, expected revisions, source hashes, target locks,
audit entries and write-recovery records provide an implementation pattern.
Existing rate/other write families are not EVV permission or a confirmation
adapter. Implement a new typed action only after obtaining its exact source
contract, preservation rules and independent authoritative readback.

Important current behavior:
  functions/src/revisions/service.ts -> callCandidates / decideCallMatch
  functions/src/revisions/records.ts -> CallMatchRecord / ExceptionReviewRecord
store LOCAL review decisions. Their hhaVerification is not_established. A local
matched or resolved record must not become a confirmed HHA event or visit.

Next bounded build:
- Draft maintenance proposal with immutable source-event references, typed
  intended action, before/proposed values, applicable rule and reviewer evidence.
- Document and validate the actual reason/action catalog and its effective scope.
- Add submit-once, fresh preflight, independent readback and unknown-outcome
  recovery to the vendor-approved action path; keep unsupported execution closed.
- Distinguish EVV reason codes from raw call-status strings and API/HTTP errors.
  A vendor error number is not an EVV correction reason.
